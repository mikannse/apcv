- (note) (idea by coach) Agent SBOM 概念：类比软件 SBOM，agent 也应当有一份"能力成分清单"，覆盖四层 tool surface，静态生成 + 动态 probe 验证，输出"声明 vs 实际"的差异（declared vs actual diff）作为第三方可验证证据

- (note) (insight by user) 企业场景定位应类比传统应用安全的 CI/CD 流程：Agent SBOM 作为部署卡点，而非实时拦截
- (decision) (by user) 考虑纳入 policy 层，定义什么样的差异结果会触发部署阻断

- (note) (by user) 对 Coverage Score + Baseline-first 的合并设计还没有理解
- (note) (by user) 提出核心挑战：agent 行为依赖提示词，baseline 与 coverage 会随 prompt 不同而变化，这样得到的结果是否可信
- (note) (by user) 讨论太过深入细节，失去了对整体项目到底是什么的感知
- (note) (idea by user) 认可 Agent Tool Fuzzer 这一定位——直接 fuzz 每个工具的实际能力边界，绕过 agent 的推理环节，结果确定性高、不受 prompt 影响
- (note) (insight by user) probe 的内容应当与业务声明的边界绑定，而不是通用的危险资源列表——边界是相对于 declared policy 而言的
- (decision) probe 的生成逻辑以 declared policy 为基准，自动生成边界之外的探针——项目定位从"安全扫描"变为"policy 一致性校验器（policy conformance validator）"
- (note) (by user) 对企业 agent 部署环境的具体配置不熟悉，需要调研
- (note) (decision) 暂停对组合 2 的深挖，横向对比组合 1 与组合 3，确认组合 2 是否最优
- (decision) 最终选定组合 2（Policy Conformance Validator）为核心方向，组合 3 的证据格式标准作为输出规范叠入组合 2
- (note) (by user) 纠正 sprint 优先级：MCP 层反而排后（已有 manifest，可见性最高）；UI 是必要的，不是可砍掉的
- (note) (by user) 企业 agent 主要基于框架编写（AgentScope、LangGraph 等），需要重新理解 runtime 内置工具在框架语境下的含义
- (note) (insight by user) 核心问题所在：真正的 tool surface 在代码里（框架内置工具 + 开发者自定义工具），没有任何统一声明，MCP 反而是最可见的一层
- (note) (by user) 提出两个问题：静态扫描能否做到框架无关？以及需要调研业界对 Agent SBOM 是否已有类似工作
- (note) (by user) 多 agent 能力合成移入 Could（后续可做）而非 Won't（不做）；对 IAM/IaC 和本项目的关系不清楚，需要解释
- (decision) IAM/IaC 自动推断 policy 移入后续调研，不列入 Won't；多 agent 能力合成同样移入 Could
- (note) (by user) 重新考虑 adversarial agent as validator（对抗性 agent 作为验证器），从 Won't 中移出
- (decision) Adversarial agent as validator 移入 Could，定位为"深度审计模式"，与确定性 probe（CI/CD gate）互补而非替代
- (note) (synthesis) 核心方向：Agent Policy Conformance Validator（agent policy 一致性校验器）——通过代码级静态扫描发现框架工具的 tool surface，依据 declared policy 自动推导边界之外的探针进行动态 probe，输出 declared vs actual 差异报告 + PASS/FAIL 结论；定位为类比 DevSecOps 中 SAST + DAST 的 agent 部署 CI/CD 安全卡点；关键洞察：policy-relative probe（相对于 policy 生成探针）同时解决了可信度与覆盖率两个问题
