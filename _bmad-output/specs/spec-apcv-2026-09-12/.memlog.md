# Agent Policy Conformance Validator (APCV) 的 Memlog

**创建日期**: 2026-09-12  
**Spec 目录**: spec-apcv-2026-09-12

---

## 初始化

**type:event** | topic="Agent Policy Conformance Validator (APCV)" — 一款开源工具，通过自动化 Probe 测试与参数追踪，验证 AI Agent 的实际能力是否符合其声明的企业策略。

---

## 核心问题陈述

**type:note** | 来自 brainstorm-summary：核心命题是"如何通过静态扫描 + 动态探测，验证 Agent 的实际能力边界与预先声明的安全策略是否一致，并产出可供第三方审计的证据，作为 DevSecOps 部署门禁"

**type:note** | 市场信号：2026 年 65% 的企业遭遇过 AI Agent 安全事件（越权访问、数据泄露、能力漂移）；目前尚不存在专门的"Agent 一致性验证工具"

---

## 动机与问题范围

**type:direction** | 为什么重要：企业部署方声称"Agent 已受限制"，却无法回答"这些限制是否真的被强制执行？"以及"我们如何证明合规？"——由此形成部署信心缺口

**type:direction** | 定位：DevSecOps 的部署前门禁（类似 SAST+DAST+Policy），而非运行时强制——与企业审计/审批流程契合，降低落地阻力

**type:direction** | 核心创新：策略相对型 Probe 生成（检验对声明边界的遵守程度，而非固定的危险项清单）+ 四层工具发现 = 确定性、可审计的验证

---

## 四层工具发现（关键洞察）

**type:capability** | CAP-1 | intent: 跨四层发现 Agent 的完整工具面 | success: 识别出 Agent 可用的 100% 工具（MCP、框架定义、运行时内建、子 Agent 继承）；在 LangGraph 上准确率 >95%

**type:constraint** | Agent 的工具面是碎片化的：MCP manifest（最易见）vs 框架代码（工具真正所在）vs 运行时能力（框架隐式提供）vs 子 Agent 组合（多 Agent 场景）——统一的 SBOM 是唯一可信来源

**type:note** | 来自头脑风暴的早期纠偏："真正的工具面在代码里，不在 MCP 里"——MCP 仅占企业 Agent 工具的约 10-20%；LangGraph/AgentScope 的工具占绝大多数

---

## 策略相对型 Probe 生成（核心创新）

**type:capability** | CAP-2 | intent: 依据声明的策略动态生成探针，而非依赖固定资源清单 | success: 对任意策略，自动生成 ≥15 个有针对性的越界测试用例；若策略边界被违反，探针即失败

**type:decision** | 策略相对型方案同时解决两个问题：(1) 确定性——测试可复现，不由 LLM 驱动；(2) 适配性——每个 agent 都获得与其声明边界匹配的定制测试集

**type:note** | 举例：Agent 声明"仅访问 /data" → 探针测试对 /etc、/home、/var 的访问；Agent 声明"仅调用 read_file 工具" → 探针测试 delete_file、write_file 的调用

**type:constraint** | Probe 生成不能依赖对抗式 LLM 迭代（依赖提示词、不确定）——改用参数级插桩包装器（wrapt decorator）追踪实际调用；这在 MVP 内可实现，且足以支撑 CI/CD 门禁

---

## 执行与验证

**type:capability** | CAP-3 | intent: 在隔离环境中执行探针并记录参数轨迹 | success: 2 分钟内完成 20-30 个探针；捕获 100% 的工具调用，性能开销 <1%；容器隔离（无交叉污染）

**type:capability** | CAP-4 | intent: 将执行轨迹与策略比对，输出差异 + 一致性判定 | success: PASS/FAIL 判定；详细违规报告（工具/参数/严重级别）；compliance_score（0-100）量化差距

**type:constraint** | 判定必须确定且可审计：基于参数级轨迹，而非行为解读 → 支撑监管合规（GDPR/SOX/ISO27001 要求提供证据）

**type:constraint** | 执行隔离要求：Docker 容器、只读文件系统、禁用网络、每个探针 <30s 超时、每次测试使用干净环境

---

## 三阶段工作流

**type:direction** | 阶段 1：静态扫描器从 Agent 代码中产出 Tool SBOM（通过 AST 解析 LangGraph 的 @tool 装饰器）

**type:direction** | 阶段 2：Probe 生成器依据声明的约束生成策略相对型测试集

**type:direction** | 阶段 3：动态执行器运行探针并记录轨迹，一致性检查器输出 PASS/FAIL + 差异报告

---

## MVP 范围

**type:capability** | CAP-5 | intent: 为 DevOps 与安全团队提供 CLI + Web UI 入口 | success: CLI（apcv validate --agent X --policy Y --output json）+ Web 看板（Agent 列表、合规评分、Policy 编辑器、执行时间线）

**type:capability** | CAP-6 | intent: 生成可用于监管审查的可审计合规报告 | success: JSON（机器）、PDF（人读）、HTML（Web）；包含执行轨迹、违规项、修复建议，格式满足审计要求

**type:capability** | CAP-7 | intent: MVP 端到端支持 LangGraph 框架 | success: 抽取全部 LangGraph 工具（静态）；生成并执行探针；给出判定；端到端延迟 <2 分钟

**type:constraint** | MVP 硬性期限：3 周；仅支持单一框架（LangGraph）；架构保持框架无关，以便后续扩展（AgentScope、AutoGen 在之后的迭代加入）

**type:constraint** | 20-30 条 Probe 规则库（初版硬编码，不由 LLM 生成）；覆盖文件系统访问、工具调用、权限提升、网络访问等类别

---

## 非目标（明确列出）

**type:note** | MVP 不做：运行时沙箱副作用追踪（过于复杂）；多框架支持（推迟到 Sprint 2）；对抗式 Agent 深度审计模式（标记为"Could Have"）；IAM/IaC 自动推断（未来方向）；端点强制（超出验证器范围）

**type:note** | 不承担的责任：Agent 沙箱/隔离的强制执行（属部署平台职责）；运行时策略执行（与一致性验证正交）；提示词注入检测（属于另一层）

---

## 成功信号与验证

**type:direction** | 产品成功：企业 DevOps 可在 CI/CD 合并前运行 APCV；获得 PASS/FAIL + 可审计差异；从而有信心将 Agent 推进到生产环境，或识别出需修复的能力缺口

**type:direction** | 技术成功：框架发现准确率 >95%；Probe 执行 <2 分钟；参数追踪开销 <1%；Docker 隔离 100%（无泄漏）；compliance_score 与人工审计复核结果一致

**type:direction** | 市场成功：没有现存工具覆盖这一细分；EU AI Act 2026 合规构成驱动力；65% 的企业事件率意味着强烈的采购动机

---

## 假设

**type:assumption** | LangGraph 可通过静态解析达到足够精度（借助 AST 解析 @tool 装饰器实现 >95% 的工具发现）

**type:assumption** | 参数级追踪对 MVP 的一致性验证已经足够（文件内容变化等次级副作用属于次要）

**type:assumption** | 目标部署环境具备 Docker（现代 CI/CD 的标准配置）

**type:assumption** | 声明的策略（YAML 形式）由 Owner 负责；MVP 不做基于 IAM/IaC 的自动推断

**type:assumption** | 合规要求（GDPR/SOX/ISO）主要关注审计留痕 + 确定性验证，而非行为层面的保证

## 待解问题

**type:question** | LangGraph 的公开 API 对基于 AST 的工具发现而言覆盖有多完整？是否存在会被遗漏的私有/隐式工具？

**type:question** | Probe 测试可接受的误报率是多少？（例如 100 个探针中有 1 个给出虚假失败，是否可接受？）

**type:question** | Policy DSL 应采用基于 Rego/OPA 的方案（业界标准但有学习曲线），还是自定义 YAML（更简单但非标准）？

**type:question** | 面向未来的多租户 SaaS：如何在不同客户的 Agent 之间隔离执行，避免交叉污染？
